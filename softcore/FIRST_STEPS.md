# Soft-core CPU on Artix-7: First Steps

This is a where-to-begin guide for the three groups on the project. It is not
a plan or a task list. Each group gets a handful of concrete first actions
and a point at which its first steps are done.

Read [ARCHITECTURE.md](ARCHITECTURE.md) first, at least sections 1–3 and the
block diagram. The sections most relevant to each group are listed below.

## Everyone

* **Agree on one shared list of on-board devices:** every sensor and device
  the board-health firmware must talk to, with its bus (UART, SPI, I²C),
  address and data rate. The board designers, FPGA developers and software
  developers all need it.
* **Estimate the log data rate** and the longest network outage the log
  buffer must bridge. This sizes the log buffer in the shell, which is frozen
  for the product's life.
* **Set up a lab network** (a separate switch or VLAN) with a boot server
  running DHCP and TFTP (e.g. `dnsmasq`) and a syslog server. The production
  servers will later be built the same way.

## Hardware designers (custom board)

Most relevant: ARCHITECTURE.md sections 6 and 8.

The shell in the flash is frozen for the product's life, and only pins the
shell exposes can ever be used. Decisions made on the board therefore stick
for 10+ years. The first steps are about the choices that can't be undone
later.

1. **Draft the FPGA pin plan in Vivado** (an I/O planning project for the
   XC7A100T-FGG484). Assign banks and voltages early and share the result
   with the FPGA developers. It will be the input to the shell design.
2. **No external RAM is needed.** The memory-module connector isn't used by
   this application; keep it only if you want it for other reasons.
3. **Configuration flash:**
   * choose a SPI flash with a **permanent lock** of its write-protection
     bits (large enough for the ~3.8 MB shell);
   * plan for x1 or x2 SPI configuration, because WP# can't be used for
     protection in quad mode;
   * make sure no FPGA pin can remove the write protection.
4. **Ethernet PHY:** the simplest option is the Nexys4DDR's LAN8720A (RMII,
   10/100), because everything proven on the Nexys then carries over. If you
   want gigabit, decide now (RGMII, or SGMII through a GTP), because the
   shell has to support it.
5. **GTP transceivers:** decide whether the 4 GTPs are routed to a connector
   or SFP, including reference clocks. If they aren't routed now, no future
   role can use them.
6. **Route spare FPGA pins** to test points or an expansion connector. The
   shell exposes every pin, so they stay usable for debugging and later
   extensions.
7. **Debug access:** a USB-JTAG + UART bridge like the Nexys4DDR's (FT2232H).
   Vivado, OpenOCD and the serial console then all work over one cable, and
   the Nexys setup works unchanged.
8. **Board health:** route board supply rails to the XADC auxiliary inputs
   (with suitable dividers), and choose I²C/SPI power monitors and
   temperature sensors with simple, well-documented register interfaces,
   since the drivers are written in-house.

**First steps done when:** a draft pin plan and the decisions on flash
device, Ethernet PHY and GTP routing have been reviewed with the FPGA
developers.

## FPGA developers (Nexys4DDR)

Most relevant: ARCHITECTURE.md sections 4, 6, 8 and 13.

1. **Install the tools:**
   * a Vivado version you're prepared to archive for the product's life;
   * LiteX (see the LiteX README for the current setup script);
   * a RISC-V bare-metal GCC toolchain;
   * OpenOCD.
2. **Build a LiteX SoC for the Nexys4DDR** with VexRiscv RV32IMC running from
   block RAM (no DDR2), LiteUART and LiteEth, and run LiteX's demo program.
   This validates the tool installation and the board.
3. **Get JTAG debugging working with upstream OpenOCD:** choose a VexRiscv
   configuration with the standard RISC-V debug interface, reach it through
   BSCANE2 over the Nexys USB cable, and halt, step and `load` a program with
   GDB. The software developers' whole debug workflow depends on this.
4. **Add the remaining peripherals** (SPI, I²C, GPIO, XADC access) and note the
   resource use: LUTs, and especially **block RAM**, which is the limiting
   resource. Start the block RAM budget from ARCHITECTURE.md section 8.
5. **Hand over to the software developers:**
   * the bitstream, written to the Nexys QSPI flash so the board boots on its
     own;
   * an OpenOCD configuration and a short README telling a non-FPGA person how
     to connect GDB and load firmware;
   * the register documentation and C headers generated by LiteX.
6. **Learn the DFX flow on something trivial:** a static region plus a
   reconfigurable partition with two versions of a blinking LED, using
   Vivado's non-project Tcl flow (UG909). Load the partial bitstream over
   JTAG first, then through ICAPE2 from logic in the static region. Record
   the 7-series restrictions you hit, and check that block RAM contents in
   the partial bitstream are initialised as expected.

Not yet: designing the real shell/role boundary or the loader. Those belong in
phase 2, once steps 4 and 6 have shown what fits and how the DFX flow behaves.

**First steps done when:** the software developers have a Nexys4DDR they can
debug with GDB, the resource and block RAM numbers are known, and a trivial
partial reconfiguration through ICAPE2 works.

## Software developers

Most relevant: ARCHITECTURE.md sections 5, 9, 10 and 11.

The first steps don't wait for the Nexys4DDR hand-over: steps 1–3 need no FPGA
hardware at all.

1. **Talk to the ChibiOS licensor:**
   * does the commercial licence cover everything you'll use, including code
     from ChibiOS-Contrib (the RISC-V port lives there)?
   * will they do or support the RISC-V port for VexRiscv?
   * do the licence and support terms cover the product's 10+ year lifetime?
2. **Create the application skeleton** in C++ on ChibiOS:
   * application logic behind a thin hardware-access layer;
   * unit tests running on the PC in ChibiOS's **POSIX simulator** port, with
     ASan, UBSan and Valgrind. This is where most bugs should be found.
3. **Start the RISC-V port** from the ChibiOS-Contrib port, in **Renode**
   (which models LiteX/VexRiscv SoCs) until the Nexys4DDR is available: system
   tick, context switch, interrupts, then a serial driver. First milestone:
   two threads and the ChibiOS shell running on the UART.
4. **Move to the Nexys4DDR** once the FPGA developers hand it over: connect
   OpenOCD + GDB from ChibiStudio or VS Code (Cortex-Debug) and load firmware
   straight into block RAM with GDB. From here, this is the daily workflow.
5. **Write the HAL low-level drivers** in this order: UART, GPIO, SPI, I²C, then
   the Ethernet MAC with lwIP. Work from the LiteX-generated register docs and
   headers; Zephyr's LiteX drivers (Apache 2.0) are useful references.
6. **Design the logging path:** syslog over UDP or TCP via lwIP, with entries
   buffered until sent. Until the shell exists, use a buffer in the role's
   block RAM; later it moves to the shell's log buffer. Include a fault
   handler that writes a crash dump (registers and stack) into the buffer.
7. **Package the environment as a devcontainer or Docker image** (RISC-V GCC,
   OpenOCD, Renode, the vendored ChibiOS sources), so onboarding and CI use
   the same environment.

**First steps done when:** ChibiOS runs threads and its shell on the Nexys4DDR,
the application's unit tests pass in the POSIX simulator, and a developer can
set breakpoints on the target from the IDE.
